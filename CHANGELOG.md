## [Unreleased]

### Added

- [Intake wording: legal and policy review](docs/research/2026-11-intake-legal-review.md): the open questions under owner decision 13 settled against EUR-Lex primary sources (GDPR, the AI Act, the Art. 28 and transfer clauses, CJEU case law), each quote checked twice, with what remains a lawyer's call in a given case.
- An MCP server, `legal-function-os-mcp` (optional `mcp` extra), with four read-only tools: `triage_requests`, `board_pack`, `dpa_review` and `legal_request_schema`. Input that breaks the request contract is rejected rather than decided. A Claude Code plugin with a marketplace (`.claude-plugin/marketplace.json`, `plugins/legal-function-os/`) installs the server and four skills (#17).
- `docs/OVERVIEW.md`: the sections that left the README (what is inside, the DPA example, the comparison with LLM legal skills, the MCP section, the suite list, known limitations, human-authored judgement). The known limitations now say that the transfer rule treats every transfer of personal data outside the EEA as HIGH risk, without distinguishing adequacy decisions.
- `make install-dev` installs the pinned tools behind `make lint`, `make coverage` and `make check`; `CONTRIBUTING.md` documents the full gate.
- The Pages index carries a `<meta name="description">` and a footer line with the commit and date it was built from (`GITHUB_SHA` in CI, otherwise "Local build").
- `legal-function-os-mcp --policy PATH` applies a policy file to every tool call, read once at start; `triage_requests` and `board_pack` also take an inline `policy` object, checked in full before use.
- `make coverage`: statement coverage of the core with a floor (96 %), pinned `coverage` in `requirements-dev.txt`, run in the CI lint job.
- CI installs a pinned Playwright and Chromium in the agent job and runs the review-room browser tests; with `REQUIRE_BROWSER_TESTS=1` a missing browser is a failure, not a skip.
- The agent runtime refuses requests whose `Host` header is not a loopback name (`127.0.0.1`, `localhost`, `[::1]`, overridable with `ALLOWED_HOSTS`), POSTs without `Content-Type: application/json` (415), bodies over 1 MiB (413, refused before reading) and a non-integer `Content-Length` (400), with tests.
- `make package-check` also checks that the wheel declares every console script, imports `legal_function_os.mcp_server` in the clean environment, runs `legal-function-os-mcp --help`, builds the sdist and runs a pinned `twine check --strict` on both distributions.
- A weekly `audit` workflow (also on every push and pull request) that runs a pinned pip-audit over the supervised agent's compiled lockfile, its pinned dev tools, the root lint pins and the floor of the optional `mcp` extra.
- An intake page (`examples/intake-page.html`, and the `intake-page` command): a static page that asks a requester the request fields, with the policy's value bands and request types, and a few more questions for the chosen type, then shows the exact file and saves it on their device as a `legal-request.v1` request file. It sends nothing (no form, no network or navigation code, and a Content-Security-Policy that blocks every fetch, form post and resource load) and decides nothing. The questions come from `intake_questions.json`, or a team's own file with `--questions`; a question can depend only on an answer given above it, which is checked when the page is built ([ADR 0006](docs/adr/0006-intake-question-files.md)). A test runs the page's own script in Node on about 11,500 answer combinations per policy and compares it with the Python reference, whose accepted files are checked against the request contract. It is generated by `make demo`, hosted on the Pages site and listed in the verification manifest.
- An approval matrix (`examples/approval-matrix.md`, `.json` and `.html`, and the `approval-matrix` command): the approval chain for every value band and risk level of the policy, the rules that add each approver and set the risk, combinations no request can reach marked as such, and each request placed in its cell. It is generated by `make demo`, hosted on the Pages site and listed in the verification manifest.
- Outcome control tower: each headline tile shows its target, the difference from it in words, and its as-of time and source. Targets are optional, under `kpi_targets` in the outcome config; the bundled config sets synthetic ones. Request rows carry their response and resolution targets in business hours.
- Review room: a "Time on this matter" section shows elapsed calendar time, business time (with legal and waiting on the business), and first response and resolution against their service levels. The outcome control tower measures it on one clock per matter: the scripted rehearsal time, or else the time the server recorded. Requesters do not see it.
- Review room: an audit-chain timeline replaces the findings, decisions and versions lists. Every event on the matter's hash chain is shown in chain order, grouped by version and marked as a command, refusal, decision or export, with its actor, role, chain position and hash prefix, and a legend with counts. The chain check comes first and covers exactly the events shown. A broken chain says which positions are verified and which are missing, links to the first event that is not verified, marks the first bad event and marks every later event as not verified; when an event's link to the one before it does not match, the one before is marked too. Requesters never see it. Findings keep their own list.
- Pilot measurement report: a "Playbook override patterns" section counts, per playbook rule, the closed matters in which reviewers kept the counterparty's wording or amended the proposal, with their reasons. A rule overridden in five or more matters within 365 days of the latest decision is listed as a proposal for the legal team. The report is deterministic and never changes the playbook.
- Review room: an "Also open" line shows which other simulated reviewer roles have the matter open and on which revision, and warns with a reload button when the matter has moved on. Presence is held in server memory for two minutes; it is never stored, logged, exported or shown to requesters (ADR 0005).
- A published request format: [`contracts/legal-request.v1.schema.json`](contracts/legal-request.v1.schema.json) and [`docs/INPUT_FORMAT.md`](docs/INPUT_FORMAT.md).
- CSV intake: `--input requests.csv` reads a request log saved from a spreadsheet, one request per row. Headers are matched loosely, yes/no answers become booleans, and Excel's comma, semicolon, tab, UTF-16 and Windows-1252 exports all work. [`examples/requests-template.csv`](examples/requests-template.csv) is a template.
- `--version` on `legal-function-os`.
- CI runs the core on Python 3.10 to 3.15, lints it with Ruff and mypy, and checks that the built wheel installs and runs (`make lint`, `make package-check`). The `mcp` job tests the server at the floor of the extra and at the latest 1.x release.
- A release workflow for PyPI trusted publishing. It stays inactive until the repository variable `PYPI_PUBLISH` is `true`.
- An offline link check for the Pages site and the Markdown docs (`make site-check`).
- A code of conduct, a root security policy, issue and pull request templates, CODEOWNERS, Dependabot, this changelog and `CITATION.cff`.
- A verification manifest in place of the portfolio proof (#11).
- The supervised agent's pilot workflow and reviewer evidence track (#13).
- Review room: inline decision forms with an error summary replace the browser prompt and confirm dialogs; resolving a comment shows the evidence cited in its thread.
- Review room: opening a synthetic matter shows the five required facts, pre-filled from the scenario, and opens the matter only when all are filled, so the first version can be submitted.
- Review room: requesters see a plain-language stage, their next step and what is withheld; reviewers see the playbook's standard and fallback position beside each change.
- One design token set (`design_tokens.py`, light and dark, contrast-tested), used by the Pages index and the review room.
- `docs/CLI.md`, the command reference the CLI help already pointed to.
- Competitive research and an adaptation plan in `docs/research/`, Round 3 of the agent's competitive research, and architecture decision records in `docs/adr/`.

### Changed

- Intake page wording, from that review: the DPA question asks who decides what the data is used for and offers a joint-controller answer; the personal-data hint covers data that can be linked to a person (IDs, IP addresses, cookie IDs, location data, coded data); the transfer hint names the UK and Switzerland as outside the EEA and asks to report any organisation or server outside it that holds, gets or sees the data; sub-processor, a person's request about their data, the date it arrived, AI uses that affect people and a meaningful human check are explained in plain words.
- `uncapped_liability` now means our side's liability is or would be uncapped: the other party asks for it, the draft sets no cap, or some claims have no cap; the usual exceptions (fraud, wilful misconduct, death or personal injury, payment of the agreed price) and a separate higher cap do not count. The intake label is "Is there unlimited liability on our side?", and the request contract's description says the same.
- A value band is the value without VAT: the highest yearly value for anything that runs longer than a year or has no end date, otherwise the total, and for a claim the amount claimed. Every band starts at its lower figure, so EUR 250,000 is `250k-1m`. The intake label for `50k-250k` reads "EUR 50,000 or more but under EUR 250,000", and the default policy's sentences read "Value over EUR 1 million.", "Value from EUR 250,000 to EUR 1 million." and "Dispute value of EUR 250,000 or more." ("Dispute above €250k." contradicted the rule it explains).
- The pilot's label for `requested_deviations` and the intake question read "Changes the other party asked for", which is true whether we buy or sell.
- Intake page wording, reviewed for requester safety: yes/no questions where an unsure No would hide a fact legal needs (sub-processors, open source, a works council, AI output that affects people, a person's request about their data) say "Not sure? Choose Yes and say why", and the security-review and human-check questions say "Not sure? Choose No"; the required follow-ups an unsure Yes opens (countries outside the EEA, personal data a supplier handles) accept "not sure", and a reply date can be "not stated"; date hints name the order (year, month and day); the transfer question covers data already sent; the employment questions ask where the person works or will work; a person's request is dated from when it first reached the company; and the contract-changes hint names the other party, customer or supplier. Points that rest on EU law are listed for a lawyer in the adaptation plan (owner decision 13). The question sheet now shows each type question's hint.
- The README is under 350 words: the one-command try-out, an example, the plugin and MCP commands, a clone quickstart that works on a clean machine (`make install && make test && make demo`), links and the licence. The claim that the `mcp` extra needs Python 3.13 under uvx is gone: it runs on Python 3.10 to 3.15 with `mcp` 1.30.0; the plugin's `.mcp.json` still pins 3.13.
- The plugin marketplace description no longer suggests an approval-matrix tool (the approval chain comes from `triage_requests`), and each skill names the tool it calls.
- The MCP tools `triage_requests` and `board_pack` no longer take a `policy_path`: a model must not pick file paths for the server to read (unreleased; no compatibility shim).
- `make lint` runs Ruff over `tests/` too, and mypy checks `raas_renderers` like every other module (the loop variables that kept it excluded have their own names now).
- The supervised agent's runtime lockfile is `supervised-agent/requirements.txt`, compiled from `requirements.in` with `uv pip compile` (`make -C supervised-agent lock`); `requirements.lock` is gone. The lockfile was recompiled with anyio, certifi, cryptography, idna, pyasn1, python-dotenv, requests and urllib3 raised to releases without known advisories. The agent's dev tools are pinned in `supervised-agent/requirements-dev.txt`, and `.github/dependabot.yml` no longer scans the agent from the root entry.
- The optional `mcp` extra needs `mcp>=1.30,<2` (ADR 0002): 1.30.0 is the first 1.x release without known advisories.
- Input is checked before any decision. An unknown `value_band` or `urgency`, a quoted boolean, a duplicate id or a misspelled field name stops the run with exit status 2 and one line per problem. An unknown `type` still goes to the General queue, with a warning and a "needs manual triage" line in the rationale.
- `pyproject.toml` carries classifiers, project URLs and keywords, and reads the version from the package.
- The README was rewritten (#16) and the case study refreshed (#12).
- Each legal source in the RaaS source manifest records its own `verified_on` date. The top-level `verified_on` is now the earliest of these dates: every source was last checked on or after it, so it is the oldest check still in force. The new `last_verified_on` is the latest. The decision pack states that range instead of the single "Verified legal-source snapshot" date it showed in 0.3.0. The Data Act, Cyber Resilience Act and GDPR entries were re-checked on 2026-10-18.
- The RaaS source manifest links the Official Journal text of each act. The AI Act and Machinery Regulation entries also link their consolidated text as of 27 July 2026 (`consolidated_url`), labelled as for information only.
- `supervised-agent/docs/demo.png` is now a rendering of real CLI output instead of a mock image.

### Fixed

- "It is not UTF-8 text (byte 0x.. at position N)" now counts N from the file's first byte; it was 3 short after a byte order mark. The legacy `--capacity-scenarios`, `--events-input` and `--outcome-config` files and `raas-deal-desk`'s input name the file and use the same sentence, and accept a byte order mark like every other JSON input.
- `init`: answers on standard input that are not UTF-8 stop the interview with a message, and a failure no longer leaves an empty policy file that blocks the next run.
- The intake checker compares labels and choice answers as they read on the page: two that differ only in spaces or invisible characters (a zero-width space, a byte order mark) are refused.
- A policy file, a JSON request file, JSON requests on standard input (`--input -`) and the files the `dpa-review`, `capacity` and `control-tower` commands read ended in a traceback when they were not UTF-8. They now say "it is not UTF-8 text (byte 0x.. at position N); save it as UTF-8" and exit with status 2, as the question file's message now also does. Standard input is judged by its bytes, so the locale no longer decides: under a C or UTF-8-mode locale bad bytes had been accepted and failed later, and on a Windows pipe valid UTF-8 could be refused. A byte order mark on standard input is accepted, as in a file.
- The legacy `--approvals` file had no error handling and was read after the board pack and the other outputs were written. It is now read with the other inputs, before anything is written; a missing, broken or wrongly shaped file stops the run, and an empty entry still means no approval.
- Intake page: a link in a question-file key the policy does not use (a request type or a value band) stopped `intake-page --out` with a traceback; the page now leaves the notes out of its data block, and they still go to standard error. A condition naming an earlier yes/no or choice question whose own key is malformed no longer gets a false "is free text" message.
- Approval matrix: `approval-matrix --policy policy.json` without `--input` failed on the bundled sample requests when the policy renamed the value bands; with `--policy` and no `--input` it now shows the policy's matrix with no request placed, as `--help` says. A blank entry in `elevated_types` marked reachable cells "Not reachable", and a cell holding a portfolio request is now always shown as reachable. The Markdown gives the reason a cell is not reachable and keeps a band name or policy value with a line break on one line. On the HTML page, long band names wrap instead of being cut off on phones or scrolling the page sideways; request IDs such as `REQ-1001` or `MAT-2026-0001` and bands such as `50k-250k` no longer break at the hyphen, and a line never starts with the comma between two IDs; placed requests are listed as "lands here" instead of with ✓, which elsewhere means pass.
- The board pack's executive summary said "**1** SLA breaches"; counts of one are singular now (also for requests handled and external-counsel referrals).
- A supervised-agent test used a made-up personal name as the rejected reviewer id; it uses "Reviewer A" now.
- Dependabot's pip updates had failed on every run since 2026-10-16: `supervised-agent/requirements.txt` only said `-r requirements.lock`, and Dependabot follows `-r` only to `.txt` or `.in` files. With the compiled lockfile named `requirements.txt`, Dependabot reads it as the output of `requirements.in`.
- The pilot's service-event ledger counted legal's time from when a requester opened a draft instead of from submission, and ended a wait on the business at the first answer while other clarifications were still open. The rehearsal outcome report and the review room now measure from submission and wait until the last open clarification is answered or resolved.
- The outcome control tower's Markdown and HTML failed when no request had a first response measured yet. They now show "n/a".
- The pilot's event-chain check failed with an error, instead of reporting a broken chain, when a stored event held a payload that is not valid JSON (or is nested too deeply to parse) or a value that cannot be hashed. It now reports "unreadable payload at seq N" or "unreadable event data at seq N". The matter history keeps a payload that parses and adds the stored text of one that does not, and the pilot measurement report no longer fails on such a payload.
- Review room presence: "older than yours" compared other reviewers with the matter's latest revision instead of the one you loaded; the stale warning kept naming the first newer revision and scrolled out of view; the presence line re-announced itself to screen readers every 30 seconds because it showed a seconds count; and expired presence entries were cleared only when the same matter was read again (loaded, written to or checked in on).
- The knowledge portal and the agent's static review-room snapshot now declare their page language.
- The review room's selects have labels, the matter list marks the open matter, and results are announced to screen readers.
- A mistyped value band such as `">1M"` was read as "no value", which turned a board-attention matter into a low-risk, reviewer-only one. It is now rejected with a suggestion.
- The workspace, agent-run and shared-space outputs counted `"awaiting_business_input": "no"` as true and split a string in `facts` or `dependencies` into characters. These optional fields are now type-checked and listed in the request schema.
- The README's DPA command printed no DPA rows; it now names the output file.
- The Pages site's "DPA clause review" card linked to a missing file.
- The CLI docstring promised a non-zero exit for board-attention items.
- `legal_function_os.__version__` said 0.2.0 in the 0.3.0 release.
- The RaaS AI Act high-risk dates follow Regulation (EU) 2026/1744: 2 December 2027 for Annex III systems and 2 August 2028 for Article 6(1) and Annex I systems. The manifest describes how machinery AI is now covered through Annex I Section B of the AI Act and Article 8 of the Machinery Regulation.
- The Machinery Regulation applies from 20 January 2027 (Article 54), not 14 January 2027.
